# Covenant Intelligence Functionality Audit

Audit date: 2026-11-03

## Scope and evidence

This audit inspected the implemented backend and frontend, ran the available automated checks, verified the current SQLite migration revision, exercised live local HTTP/CORS requests, reviewed the synthetic demo seed, and later attempted one real provider extraction using only a synthetic agreement. No application architecture was redesigned. Reliability fixes were made to the demo seed and provider-error reporting; a reviewer test fixture now looks up the configured reviewer by ID. No existing database was reset or deleted.

## Implemented functionality

- **Agreements and document versions:** create/list agreements; upload PDF versions; retain the original PDF in local storage; process PDF text by page; retain page text and SHA-256 hashes; inspect page text and download the original PDF.
- **Extraction:** extraction runs create draft candidates and keep provider/run metadata. The pipeline uses chunking, prompts, an OpenRouter-compatible provider adapter, a canonical Pydantic obligation schema, and deterministic validation for schema and evidence traceability. Evidence is represented in each immutable `canonical_payload` and in relational `Evidence` rows.
- **Definitions and references:** the extraction module resolves defined terms and cross-references using document text/context and records the result with evidence. This is a traceability aid; it does not establish legal interpretation or completeness.
- **Human review:** reviewers can inspect candidates and supporting pages/evidence, then approve, correct, reject, or request more information. Corrections replace the complete canonical obligation object and are revalidated, including evidence, before approval. Candidate payloads remain unchanged; approved revisions preserve the full approved payload and relational evidence.
- **Approved register:** list/detail/revision views expose approved obligations and revision history.
- **Quarterly monitoring:** create periods and record status updates/evidence references; overdue is derived from due date and status. The supported states are `awaiting_setup`, `upcoming`, `due`, `awaiting_evidence`, `submitted`, `reviewed`, `not_assessed`, and `not_applicable`.
- **Amendments:** compare selected agreement versions and review proposed additions, changes, and possible removals. Removal approval requires an explicit full-document review confirmation in the UI/API workflow. Decisions are audited.
- **Audit history:** query and filter audit events generated by agreement/version, extraction, review, monitoring, amendment, and related workflow operations.
- **Workspace boundary:** API dependencies scope agreement/workflow access to the seeded development workspace and map development reviewer identities to roles.
- **Frontend views:** Dashboard, Agreements, Covenant Register, Review Queue, Obligation Tracker, Amendment Comparison, and Audit History are present in the React application.

## Extraction quality and limitations

- Unit/integration tests use a mock provider; they verify request/response and error handling, not extraction accuracy.
- One actual OpenRouter extraction attempt was made with the configured model using a synthetic demo agreement. The provider returned HTTP 402 (`provider_insufficient_credits`); the run ended partial with zero candidates. No model response was available to validate, so quote fidelity, definition/reference resolution quality, and extraction completeness could not be evaluated. There are no model accuracy/recall metrics to report. The sanitized run record is [LLM_LIVE_EVALUATION_2026-11-03.json](LLM_LIVE_EVALUATION_2026-11-03.json).
- Synthetic demo candidates are clearly marked as fixtures and are not model outputs.
- Definitions and references are retained/resolved as candidate context but remain subject to reviewer verification. Ambiguous and unsupported conditions must remain in review.
- PDF processing extracts embedded text with PyMuPDF. Scanned-image OCR is not implemented.
- The application does not calculate actual borrower financial ratios or covenant headroom, connect to ERP systems, or provide binding legal advice.
- The single seeded development workspace and header-selected development identities are not production authentication or identity management.
- Amendment comparison is a review aid; a comparison can remain `ready_for_review` while proposals are pending. Every proposed addition/change/removal needs human disposition.
- Docker/PostgreSQL was not independently verified during this audit. Current successful migration and API checks used SQLite.

## Security and local data notes

- Scanned 93 source/config text files (excluding `.env`, example environment file, local database, PDFs, runtime storage, dependencies, build output, and caches): no high-confidence API-key/token patterns found.
- `.env.example` contains placeholder values for OpenRouter credentials/model and the local PostgreSQL password; the base URL and non-secret application defaults are explicit configuration values. `.env` exists, is ignored by `.gitignore`, and its contents were not read or printed.
- The database and runtime PDF storage are excluded from source-control patterns. Database metadata reports all 8 stored agreement versions as `synthetic`; there are 8 runtime PDFs. Their bytes were not copied or disclosed in this report.
- No files were deleted, no database was reset, and no Git push or archive was performed.
- This workspace directory has no `.git` metadata, so staged/untracked Git status could not be inspected here.

## Known issues and remaining work

1. The live provider was reached but returned HTTP 402 for insufficient credits. Provider/model compatibility beyond request acceptance, actual evidence-quote fidelity, and extraction completeness remain unverified until a response can be returned. Use only synthetic/public documents for a later live evaluation.
2. The existing seeded amendment comparison includes an ineligible candidate that fails evidence-condition validation with HTTP 422; it remains pending for reviewer disposition. A separate valid proposal was accepted, leaving the comparison awaiting review of its other proposal.
3. Browser UI automation and visual accessibility checks were unavailable in this environment. Human review, upload, monitoring, amendment, and audit screens need a browser-level pass when local browser automation is enabled.
4. PostgreSQL migration/integration behavior and Docker Compose startup remain unverified. SQLite tests passing do not establish PostgreSQL compatibility.
5. The current workstation used API port 8001 because port 8000 was occupied by another process; the Vite server is at 5173. Open `http://127.0.0.1:5173` for the frontend and `http://127.0.0.1:8001/health` for the API health check while these local processes remain running.
6. The 402 extraction's initial immutable application audit entry predates the provider-error metadata fix and contains only status/count. A supplemental row was not added to the existing local database because the approval reviewer rejected that mutation. The exact sanitized reason is in the linked evaluation JSON; future provider-failure audit events retain the safe error code, HTTP status, and message, verified by the backend suite.
